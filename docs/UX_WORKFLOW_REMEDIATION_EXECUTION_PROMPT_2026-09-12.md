# UX 작업 흐름 개선 실행 프롬프트

아래 내용을 그대로 작업 지시 프롬프트로 사용한다.

---

현재 저장소는 `C:\Git\easy_labeling`이다. 먼저 `docs/UX_WORKFLOW_REMEDIATION_PLAN_2026-09-12.md`를 끝까지 읽고, 이 문서를 작업 범위·결정 기록·진척도의 단일 기준으로 사용하라.

목표는 I-01~I-04를 계획된 순서대로 구현하고 검증하는 것이다. 단순히 UI 클래스만 조정하지 말고, 화면에 보이는 활성 상태와 실제 작업 상태가 일치하도록 수정하라.

작업 전 규칙:

1. `git status --short`로 기존 사용자 변경을 확인하고 보존하라.
2. 확정된 결정은 `D-01 A, D-02 A, D-03 A, D-04 A`다. 다른 선택지로 임의 변경하지 마라.
3. Phase 3의 코드를 수정하기 전에 현재 왼쪽 레일 선택별 왼쪽 내용과 오른쪽 작업공간/Inspector 기능을 실제 UI와 코드로 재확인하고, 계획 문서의 현행 결합표를 완성하라.
4. 각 현상은 현재 동작을 재현하는 실패 테스트를 먼저 만들고, 최소 범위의 구현으로 통과시켜라.
5. 각 Phase를 시작/종료할 때 계획 문서의 상태와 진척표를 즉시 갱신하라.
6. 무관한 리팩터링, 포맷 변경, 기능 추가는 하지 마라.

구현 순서:

1. Phase 0: 의사결정과 상태 매트릭스 고정
2. Phase 1: Segmentation 기본 Paint 클래스 및 숫자키 도구 유지
3. Phase 2: Algorithm Input의 Setup/실행/Batch 입력 계약 통일
4. Phase 3: Detection의 왼쪽 작업공간, 상단 도구, 오른쪽 Inspector 상태 분리
5. Phase 4: 전체 자동 테스트와 데스크톱/390px 수동 검증

핵심 구현 계약:

- I-01: D-01 A라면 클래스 `1`을 우선 선택하고, 없으면 첫 양수 클래스를 선택한다. 양수 클래스가 없을 때만 그리기 도구를 막는다. 배경 `0`은 기본 Paint 클래스로 쓰지 않는다.
- I-02: 주 키보드와 숫자패드의 숫자 `1`~`9`는 클래스만 변경하고 Brush, Polygon, Superpixel, AI Select, Edit, Erase 등 현재 도구를 바꾸지 않는다. D-02 A에서는 주 키보드와 숫자패드의 `0`만 기존처럼 Erase로 전환한다. `KeyboardEvent.key`, `code`, `location`을 안전하게 정규화하고 Num Lock이 꺼진 숫자패드 탐색키와 입력 필드/모달 입력은 가로채지 마라.
- I-03: 현재 코드는 Algorithm Input을 실행 엔진의 현재/프리셋/Batch 경로에는 이미 적용하지만 Setup의 이미지·ROI·preview에는 일관되게 반영하지 않는다. “전혀 미적용”으로 오진하지 마라. D-03 A에서는 공용 전처리를 기본 입력에 한 번 적용하고, Template Matching 고유 preprocessing을 그 뒤에 한 번 적용한다. Setup과 실행이 같은 기본 픽셀 계약을 사용하도록 만들고 현재 Base input 상태를 화면에 표시하라.
- I-04: D-04 A에서는 왼쪽 레일이 작업공간, 상단 버튼이 도구, 오른쪽이 Inspector를 담당한다. Draw/Edit/Automation 전환이 왼쪽 탭을 강제로 바꾸거나 모두 비활성으로 만들면 안 된다. 구현 전에 Files, Annotate, Display, Preprocess, Review 선택 시 현재 오른쪽에 나타나는 기능, 활성 Inspector 탭, 패널 열림/닫힘과 도구 상태를 전부 목록화하고 목표 상태와 나란히 비교하라. 기존 단일 `activeTask`를 그대로 조건문만 덧붙여 유지하지 말고, 역할별 상태를 분리하되 호환 계층으로 변경 범위를 통제하라.

테스트 요구사항:

- Segmentation: 기본 클래스 1, 클래스 1 부재, 양수 클래스 부재, 빈 마스크, 저장 마스크 복원, 이미지 전환을 검사하라.
- 숫자키: 주 키보드와 숫자패드 각각에서 최소 Polygon→2, AI Select→3, Edit→4, Erase→5의 도구 유지와 클래스 변경을 함께 검사하고 0의 계약, Num Lock 해제 탐색키, 입력 필드/모달 보호를 별도로 검사하라.
- Algorithm Input: Original/Processed 각각에서 Setup preview, ROI, 현재 실행, 저장 프리셋, Batch가 같은 기본 입력 계약을 사용함을 검사하라. 공용 및 템플릿 전처리의 중복 적용도 검사하라.
- Detection 상태: 모든 왼쪽 탭 × Draw/Edit/Automation에 대해 현행 및 기대 매트릭스를 먼저 작성하라. 왼쪽 내용, 오른쪽 기능, Inspector 탭, 패널 표시 상태, 활성 도구를 각각 assertion으로 연결하고 대표 사용자 흐름을 E2E로 검증하라.
- 마지막에 `npm run typecheck`, `npm run test:unit`, `npm run build`, `npm run test:e2e`를 실행하라.

진행 보고 방식:

- 각 Phase가 끝날 때 변경 파일, 통과한 수용 기준, 실행한 테스트와 결과, 남은 위험을 계획 문서에 기록하라.
- 실패가 발생하면 재현 명령과 핵심 오류를 기록하고, 기존 실패인지 신규 회귀인지 근거로 구분하라.
- 사용자에게는 완료된 항목 수와 현재 Phase를 간결하게 보고하라.
- 모든 수용 기준과 회귀 검증이 통과하기 전에는 `완료`로 표시하지 마라.
- 사용자가 새 현상을 추가하면 계획 문서에 다음 ID로 등록하고 재현/원인/수용 기준을 먼저 작성한 뒤 기존 우선순위에 반영하라.

최종 보고에는 I-01~I-04별 결과, 확정한 D-01~D-04, 테스트 통과/실패 수, 미해결 위험, 계획 문서 링크를 포함하라. 사용자가 명시적으로 요청하지 않는 한 커밋하지 마라.
