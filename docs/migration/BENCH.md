### 3단계: TIFF 8bit gray 디코드 (2026-10-30)

앱의 실제 디코더(`decodeImageForAutomation`)로 쟀다. 같은 앱에서 네이티브로 한 번, `easyLabelingNativeOff = ["tiff"]`로 tiff.js 경로를 한 번 돌렸고, 3회 중앙값이다. UI는 그 사이 가장 긴 long task다.

| 입력 | tiff.js (TS 경로) | 네이티브 | 배수 |
|---|---|---|---:|
| 2048×1536 무압축 | 279ms (UI 0) | 90ms (UI 0) | 3.1x |
| 2048×1536 LZW | 450ms (UI 104) | 94ms (UI 0) | 4.8x |
| 2048×1536 LZW + predictor | 407ms (UI 149) | 91ms (UI 0) | 4.5x |
| 2048×1536 Deflate | 474ms (UI 191) | 59ms (UI 0) | 8.0x |
| 2048×1536 PackBits | 336ms (UI 52) | 93ms (UI 0) | 3.6x |
| 4096×3072 무압축 | 1,270ms (UI 211) | 184ms (UI 0) | 6.9x |
| 4096×3072 LZW | 1,462ms (UI 502) | 340ms (UI 0) | 4.3x |
| 4096×3072 LZW + predictor | 1,685ms (UI 538) | 323ms (UI 0) | 5.2x |
| 4096×3072 Deflate | 1,387ms (UI 388) | 247ms (UI 0) | 5.6x |
| 4096×3072 PackBits | 1,396ms (UI 237) | 206ms (UI 0) | 6.8x |

- 입력: PIL로 만든 SEM 형태 합성 이미지(노이즈가 많아 압축률은 낮다)이고, 픽셀은 모두 같다.
- 데스크톱 e2e(`tauri-desktop.spec.ts`)의 무압축 측정값: 2048은 39~42ms 대 302~362ms, 4096은 129~159ms 대 1,189~1,242ms.
- 기준값 분해(TS 경로, 4096 무압축): 파일 읽기 IPC 241ms + tiff.js 88ms + PNG 재인코드 635ms + img 디코드 258ms. 네이티브는 읽기와 PNG 단계를 없애고, 디코드를 UI 스레드 밖에서 한다.
- 영향: 폴더 Review의 TS 경로 측정값도 바뀌었다(60장 TIFF 26초 → 14.5초). 이 측정은 review·label-scan만 끄기 때문에, 크기 확인 디코드에 이제 네이티브 TIFF가 쓰인다. 2단계 표의 TS 값은 3단계 이전 기준이다.

### 4단계: 네이티브 TIFF 픽셀 상주 (2026-10-30)

데스크톱 e2e(`tauri-desktop.spec.ts`, 디버그 exe)로 쟀다. 같은 4096×3072 무압축 TIFF를 상주 경로(기본)와 업로드 경로(`easyLabelingNativeOff = ["tiff"]`, tiff.js로 열어 페이지가 픽셀을 추출·업로드)로 열었고, 4회 측정했다.

| 단계 | 업로드 경로 | 상주 경로 |
|---|---|---|
| Processed 첫 전환 (Q, 기본 설정) | 710~1,062ms, 중앙값 811ms | 562~701ms, 중앙값 615ms |
| 그중 가장 긴 UI 정지 | 226~271ms (픽셀 추출) | 193~233ms (결과 표시) |
| 첫 refine (원본, 40박스, 이미지 적재 포함) | 378~473ms | 20~40ms |

- 구간 측정(일회성): 업로드 경로는 Q 직후 메인 스레드 픽셀 추출 260~440ms가 있고, 그다음 업로드가 이어진다. 상주 경로는 `preprocess_view_load_tiff`가 20~28ms다.
- 처음에는 회색→luma 변환을 src-tauri에 두어 이 단계가 120~140ms였다. 디버그 빌드에서 src-tauri는 최적화되지 않기 때문이다. 변환을 el-core(`gray_luma`)로 옮겨 해결했다.
- 남은 UI 정지(약 0.2초)는 결과가 도착한 뒤의 RGBA 조립과 캔버스 쓰기로, 두 경로에 공통이다.

### 6단계: 슈퍼픽셀, Processed 입력, 원본 픽셀, 미리 디코드 (2026-10-30)

순수 계산(같은 입력, 기본 설정, 영역 크기 16). Rust는 `cargo bench -p el-bench --bench core -- superpixels`, TS는 `node scripts/bench/core.mjs --filter superpixels --runs 3`이다.

측정 조건 (2026-10-29):
- 장비: i5-8600K 6코어/6스레드, Windows 10.
- 측정 중 다른 프로세스의 CPU 사용 약 20~30%(svchost, docker 등)가 있었다. 절대값은 그만큼 보수적이고, TS와 Rust는 같은 조건에서 연달아 쟀다.

- TS: `node scripts/bench/core.mjs --runs 30`. 워밍업 3회 후 30회 측정했다.
- 모두 IPC를 뺀 순수 계산 시간이다. 앱 안에서의 시간(IPC 포함)은 각 단계에서 따로 잰다.

요약:
- refine은 순수 계산 기준 **약 12~13배** 빠르다(2048×1536, 500박스: 134ms → 10ms). Tauri 앱에서는 이미 Rust 경로를 쓰고 있다.
- `tests/e2e/tauri-desktop.spec.ts`가 출력하는 "native N ms, js M ms"는 비교 근거로 쓰지 않는다. 박스 40개를 1회만 돌리고, 먼저 도는 네이티브 쪽이 worker 생성·이미지 업로드·스레드풀 초기화를 떠안는 동등성 테스트의 로그이기 때문이다(2026-10-29 실행: native 506ms, js 330ms).
- Processed 보기 전처리는 **약 5~7배** 빠르다. 사용자가 체감하는 지점은 "4096×3072 heavy 설정에서 화면 정지 약 5.0초 → 약 0.9초(백그라운드)"이다. 1단계 이식의 근거.
- 1단계 결과(앱 안): 4096×3072에서 무거운 설정 적용 시 **UI 정지 약 5.8초 → 최대 0.2초**, 결과 표시까지 약 1.5초.
- 기본 설정의 첫 전환은 결과 표시까지의 시간이 TS와 비슷하다(약 1.1~1.3초). 차이는 UI가 그동안 멈추지 않는다는 점이다(최대 0.3초).
- 처음 구현은 raw IPC 업로드 때문에 첫 전환이 5.9초로 오히려 느렸다. SharedBuffer로 바꿔 해결했다(D-006).

### Refine 축 세트(상하·좌우) (2026-10-31, `81095dfa`+작업트리)

### Refine 폴더 실행 (All images in folder) 단계별 시간 (2026-11-05, `7a75516f`+작업트리 v2.39.1)

`tests/e2e/folder-run-performance.spec.ts`(Tauri 디버그 exe, el-core는 opt-level 3), 데이터셋은 `scripts/bench/make-folder-run-dataset.py`: 200장, 2048×1536 8-bit gray, 이미지당 박스 100개, 기본 refine 설정(Original). 값은 실행이 보고한 `data-timings`(1회). SMB는 `\localhost\D$` 루프백이라 네트워크 지연은 없고 SMB 프로토콜 비용만 들어간다(실제 NAS는 이보다 느리다). lanes = 라벨 파일 동시 쓰기 수(1 = 2.39.0까지의 하나씩 쓰기).

- refine 계산 자체는 이미지당 약 20ms(IPC 포함)로 작다.
