# Detection 대량 박스 처리 성능 기록

측정일: 2026-09-09
대상: Detection 모드의 다중 복사·붙여넣기와 Layout 적용

## 원인과 적용

기존 흐름은 붙여넣기/레이아웃 적용 시 각 박스마다 Fabric 객체와 캔버스 라벨을 만들고, 기본 `renderOnAddRemove` 상태에서 추가·삭제를 반복했다. 대량 선택에서는 라벨 객체도 모든 박스에 생성되어, 화면 밖 객체까지 렌더링 비용과 메모리를 사용했다.

이번 변경은 다음 원칙으로 처리한다.

- 250개 이상 선택 시에만 활성 작업 패널을 열고, `복사`, `박스 생성`, `화면 반영`, `Undo 상태 저장` 단계를 표시한다.
- 대량 삭제도 같은 패널에서 `선택 박스 제거 → Undo 상태 저장`을 표시한다. 이미 삭제를 시작한 단계는 원자적 복구가 보장되지 않아 Stop 버튼을 제공하지 않는다.
- 붙여넣기와 Layout 적용은 기본 100개 단위로 `requestAnimationFrame` 사이에 양보한다. 각 청크 뒤 진행률은 `현재 / 전체 boxes` 형식으로 업데이트된다.
- 청크 진행 중에는 Fabric의 자동 객체별 렌더링을 끄고, 완료 시 한 번만 화면 반영을 요청한다.
- 붙여넣기 대상이 250개를 초과하면 Fabric의 대형 `ActiveSelection`을 새로 만들지 않는다. 이 객체는 모든 멤버의 좌표를 다시 계산하므로, 대량 작업에서는 화면 멈춤의 원인이 된다. 소량 붙여넣기는 기존처럼 결과 전체를 선택한다.
- 캔버스 라벨은 현재 보이는 영역에서 실제로 표시될 후보에만 생성한다. 박스·클래스·색상·ID·좌표 데이터는 생략하지 않는다.
- 취소 가능한 붙여넣기/Layout 적용은 생성 중인 박스를 모두 되돌린다. Layout의 `replaceExisting`도 신규 박스 생성이 완전히 끝난 뒤 기존 박스를 교체한다.
- 대량 삭제도 객체별 자동 렌더링을 억제하고 최종 한 번만 렌더한다. 이동과 기존 단축키의 데이터 의미는 유지한다.

## 검증 측정

다음 값은 `tests/unit/performance/detection-bulk-performance.test.ts`의 Fake Fabric 회귀 측정값이다. Heap 증감은 Node 프로세스의 측정 전후 값이라 GC 시점에 따라 달라진다. 실제 GPU/브라우저 렌더러 시간은 PC와 이미지 크기에 따라 다르므로, 이 표는 데이터 처리와 렌더 요청 수의 회귀 기준으로 사용한다.

| 붙여넣기 박스 수 | 처리 시간 | 최종 렌더 요청 | 캔버스 객체 수(박스+가시 라벨) | Heap 증감 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 19.5 ms | 1 | 214 | +2.4 MB |
| 500 | 18.6 ms | 1 | 1,022 | +3.5 MB |
| 1,000 | 58.1 ms | 1 | 2,030 | +6.1 MB |
| 5,000 | 453.9 ms | 1 | 10,094 | +15.7 MB |

별도 5,000개 회귀 테스트에서 붙여넣기 후 Undo/Redo까지 1,196 ms, 5,000개 Layout 적용 후 Undo까지 1,020 ms로 통과했다. 라벨을 모든 객체에 즉시 만들던 이전 구현은 같은 5,000개 붙여넣기·Undo/Redo 테스트가 5초 제한을 초과했다.

## 정합성 검증

- 대량 붙여넣기는 한 개의 History entry만 만든다. Undo 한 번으로 전체가 사라지고 Redo로 전체가 복원된다.
- 취소 시 새 박스와 새 라벨을 제거하고 기존 선택 상태를 복원하며 History entry를 만들지 않는다.
- Layout은 5,000개 적용을 하나의 History entry로 기록한다.
- Detection workflow의 캔버스 controller만 변경하므로 Segmentation 마스크 document는 읽거나 수정하지 않는다.
- 자동 저장은 document mutation이 대량 명령 완료 후 한 번 발생하므로, 작업 중 저장이 반복 실행되지 않는다.
- `tests/e2e/detection-bulk-operation.spec.ts`는 실제 샘플 workspace에서 5,000개를 선택한 뒤 `Ctrl+C`/`Ctrl+V`를 입력해 진행 패널, 10,000개 완료 상태, Undo 복귀를 확인한다.
- 2026-09-09에 최신 Vite 번들(`127.0.0.1:4174`)에서 위 Chromium 시나리오를 실행해 통과했다.

## 남은 제약과 후속 확인

- 이 기록은 실제 Chromium/Electron의 GPU Paint·메모리 프로파일이 아니라 결정론적 Fake Fabric 측정이다. 릴리스 전 성능 탭에서 DevTools Performance/Memory로 동일 100·500·1,000·5,000개 시나리오를 한 번 더 수집해야 한다.
- 복사 원본을 Fabric이 deep clone하는 첫 단계는 라이브러리 내부 동기 비용이 남아 있다. 현재는 복사 전후와 생성 청크 사이에서 상태가 표시되며, 취소는 clone 완료 직후 안전 지점에서 반영된다.
- 드래그 이동·줌·화면 이동은 기존 Fabric 이벤트 모델을 유지한다. 실제 5,000개 이미지에서 프레임 저하가 남으면, 다음 단계로 객체 culling 또는 label layout worker를 검토한다.
