# Easy Labeling UI·UX 및 주요 기능 점검

점검일: 2026-10-06 · 대상: `C:\Git\easy_labeling`의 현재 작업 트리와 YOLOE-26 Windows 실행 파일.

**주요 기능은 상당 부분 동작하지만, 확대 입력과 ROI 선택의 기능 결함, 도구 상태와 화면 배치 문제가 있습니다.** 우선 확대 비율·버튼의 오류와 Detection 전처리의 ROI 선택 충돌을 수정하고, YOLOE 팝업의 작업 버튼을 항상 보이게 한 뒤, Review와 클래스 설정의 정보 구조를 정리하는 순서를 권장합니다. 전체 색상이나 테마를 바꾸기보다 현재의 파란색 작업 버튼, 양쪽 패널, 팝업 방식을 유지하면서 정리하는 방향입니다.

이번 작업은 감사와 개선안 작성입니다. 프로그램 소스는 수정하지 않았습니다. HEAD `9433d53`만의 평가가 아니라, 기존에 수정 중이던 프리셋·일괄 실행·GPU 표시 기능을 포함한 현재 상태를 평가했습니다.

## 1. 점검 범위와 방법

- 별도 브라우저 탭의 `http://127.0.0.1:4174/`에서 기본 기능, 팝업, 샘플 데이터, 라이트·다크 테마를 직접 조작했습니다. 사용자의 기존 `localhost:4173` 탭과 데이터는 점검 대상으로 변경하지 않았습니다.
- 1332×1244와 1280×720 화면을 비교했습니다. 실제 화면 캡처 31장과 이번 실행에서 얻은 Windows 앱 캡처 4장을 보관했습니다.
- 타입 검사, 빌드, 단위 테스트, Chromium E2E 전체 테스트를 실행했습니다. 실패한 테스트는 재실행과 대기 조건을 보강한 비교 실행으로 분리했습니다.
- 별도 데이터·프리셋 폴더를 사용하는 Windows 실행 파일에서 실제 ONNX GPU/CPU 추론, Detection/Segmentation 전체 이미지 처리, 저장·재시작·복원을 확인했습니다.
- 기능이 동작하는지와 사용자가 쉽게 찾고 이해할 수 있는지는 별도로 평가했습니다. 실제 모델의 출력이 만들어졌다는 사실을 산업 도메인 정확도 검증으로 취급하지 않았습니다.

화면별 동작, 상태, 원본 캡처는 [35단계 화면 기록](ux-audit/20261006/index.md)에 모두 정리했습니다. 이전 보고서의 화면을 이번 점검 근거로 재사용하지 않았습니다.

## 3. 유지할 부분

- Annotate/Mask로 통합된 편집 탭과 맨 아래 Review 배치. 다시 중복 Files 탭을 만들 필요는 없습니다.
- 테마에 맞춘 ONNX 파일 선택, 선택 파일명 유지, 이미 축소된 Labeled/Unlabeled 체크박스.
- 모델 크기·GPU/CPU·해상도 설정, 기존 라벨의 샘플 활용, 서로 다른 이미지의 예시, 프리셋 저장·복원 기능 자체.
- 결과를 별도 라벨 폴더로 저장하고 원본을 보존하는 방향.
- 주 작업을 파란 버튼으로 강조하는 방식, 클래스 색상, 그룹 접기, 현재 팝업의 큰 이미지 영역.
- 확대·팬 중 샘플 좌표를 유지하고, Preview에서 라벨을 변경하지 않는 동작.

### 기능 결함 U01의 연결 근거

`src/bootstrap/event-manager-adapter.ts`의 Select ROI 클릭은 `beginSegmentationSrRoiSelection`을 호출합니다. 관련 선택 처리는 `src/features/segmentation/workflow.ts`에 있습니다. 현재 Detection에서 이 선택 상태가 활성화되지 않은 채 일반 Draw 입력으로 이어지는 현상을 화면에서 재현했습니다. **정확한 수정 위치는 모드별 캔버스 입력 경로를 함께 확인해 결정해야 합니다.** 클래스 팝업은 취소했고 샘플의 원래 207박스를 보존했습니다.

### 입력 소스 U19의 코드 근거

`src/bootstrap/yoloe-controller.ts`는 샘플의 `sourceImage`와 현재 `state.session.currentImage`를 `imagePng`로 직렬화합니다. `src/features/inference/yoloe.ts`의 `imagePng`는 해당 이미지 자체를 PNG로 그리며 전처리 설정을 인자로 받지 않습니다. 화면의 Processed 표시가 YOLOE 입력에도 적용됐다고 안내하면 안 됩니다. 입력 소스를 명시하고, 전처리 입력을 지원하려면 샘플과 추론 이미지에 같은 변환을 실제로 연결해야 합니다.

### 확대 기능 U23의 연결 근거

전체 E2E 실행 중 `setZoomPercentage`의 `canvas.getCenter` 오류가 Vite 런타임 로그에 나타났습니다. 이어 실제 점검 탭에서 샘플을 로드한 뒤 Detection/Segmentation 각각 Fit 56% → 125% 입력 → 다른 컨트롤로 포커스 이동 → 확대/축소 버튼을 실행했습니다. 입력은 125%지만 1157픽셀 폭 이미지가 약 650픽셀 폭으로 계속 표시됐으며 버튼 클릭에서도 같은 오류를 확인했습니다. `src/features/canvas/canvas-shell.ts`의 `setZoomPercentage`와 `zoom`은 모두 `getCenter()`를 호출합니다. 휠 확대와 Fit의 정상 동작만으로 이 경로까지 통과 판정하면 안 됩니다.

| worker roundtrip, OpenCV init, 긴 실행 시간 목록 | 실행 상세로 이동 | 기본은 `매칭 1개 · 99.96%` |
| 전체 이미지에 반복되는 실패 사유 | 상태 요약과 행별 펼치기 | `대상 없음 · 임계값 미달` |
| `No labels match current filter` | 빈 상태에 맞게 변경 | 이미지 없음: `이미지를 열어 시작하세요`; 실제 필터 없음: `조건에 맞는 라벨이 없습니다` |
| Processed/Original/AI 입력 설명 | **유지하되 구체화** | `화면: 전처리 결과 · YOLOE 입력: 원본` |
| Preview는 라벨을 변경하지 않음, 좌표는 원본 기준, 덮어쓰기 대상 | **유지** | `미리보기 · 라벨 변경 없음`, `좌표: 원본 기준`, `기존 결과를 갱신합니다` |
| 줌·팬 사용 설명 | 한 줄·도구 도움말로 축약 | `Ctrl+휠 확대 · Ctrl+드래그 이동` |

프로그램이 영어 UI를 사용 중이므로 위 한국어는 의미를 설명하는 예시입니다. 실제 적용에서는 기존 언어 정책을 유지하고, 버튼마다 영어/한국어를 혼용하지 않는 방향이 좋습니다.

### 클래스와 결과 표시

Mask Inspector는 클래스 색·이름·현재 칠할 클래스·표시 여부를 한 행에 모읍니다. 선택된 클래스와 숨겨진 클래스는 다른 상태 표시를 사용합니다. Detection과 YOLOE Preview는 같은 라벨 선·배지 규칙을 공유하고, 밝은 클래스 색상의 글자는 자동으로 검게 표시합니다. 클래스명·점수는 유지하되 디버그 숫자를 섞지 않습니다.

### 결과 목록

Template 배치는 `완료 17 · 매칭 1 · 대상 없음 16 · 오류 0`을 먼저 보여주고 파일별 결과는 표로 표시합니다. 대상 없음은 정상적인 결과이며, 실제 모델·파일·저장 오류만 빨간색으로 처리합니다. YOLOE도 결과 0개를 오류와 구분하되, 빈 결과가 저장되는 경우는 사용자에게 분명히 알려야 합니다.

## 7. 적용 순서와 검증 조건

| 단계 | 적용 항목 | 단계 완료 조건 |
|---|---|---|
| 1 · 잘못된 동작과 주 작업 접근성 | U01 ROI 충돌, U23 확대 입력·버튼, U02 팝업 고정 작업, U05 도구 상태, U06 저장 의미, U07 진행 상태 | 두 모드에서 올바른 입력·저장 대상·실제 확대 비율, 1280×720에서 실행 버튼 접근, CPU 첫 실행 상태 확인 |
| 2 · 정보 구조와 반복 작업 | U03 Review, U04 클래스, U10~U20 설정·목록·입력 소스 정리 | 처음 사용자 작업 흐름과 숙련자의 다중 샘플·배치 흐름을 모두 확인. 기존 기능과 프리셋 호환 유지 |
| 3 · 시각 품질과 일관성 | U08/U09 대비·배지, U21/U22 빈 상태·패널·접근성 | 두 테마, 작은 객체, 밝은 색상, 좁은 화면, 키보드 포커스 확인 |

각 단계 후 타입/빌드와 관련 테스트를 실행합니다. 저장·입력·라벨 변환을 바꾸는 단계는 실제 GPU/CPU 실행과 원본 파일 비교도 함께 검증합니다. CSS·문구만 바꾸는 항목에 별도 중복 단위 테스트를 늘릴 필요는 없습니다.

기존 E2E는 작은 화면에서 팝업 자체가 보이는지 확인하지만 **핵심 작업 버튼이 스크롤 없이 보이는지까지는 확인하지 않습니다.** 이 조건을 추가하고, 대량 편집 테스트의 이미지·라벨 준비 완료 대기도 보강하는 것이 좋습니다.

추가로 남은 확인 범위는 전체 포맷 왕복, 실제 M/L·2048 ONNX 실행, 산업 데이터 정답 기반 정확도, 키보드 전용 전체 흐름, 여러 실제 GPU 장치와 OS 환경입니다. 현재 결과로 이 범위까지 통과했다고 판정하지 않았습니다.
